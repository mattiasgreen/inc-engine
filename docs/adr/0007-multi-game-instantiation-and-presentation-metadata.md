# Multi-Game Instantiation and Declarative Presentation Metadata

To prove that `inc-engine` can power mechanically and narratively distinct games without game-specific logic in the engine or UI shell, multiple complete **GameConfig** definitions are instantiated and verified side by side.

1. **Data-Driven Presentation in `GameConfig`**: A `GameConfig` may include declarative presentation fields (`subtitle`, `palette`, `character`, `lore`, `svg`, and action verbs such as `prestige.actionLabel`). The functional core (`src/engine/core.js`) ignores presentation fields, while the imperative UI shell (`src/ui/app.js`) binds all labels, CSS custom properties, inline SVG artwork, and narrative chronicles directly from the active `GameConfig` with zero hardcoded strings in `index.html` or `app.js`.
2. **Progressive Narrative and Character Guide**: Narrative progression uses the existing **Visibility State** (`stats.visibility`) derived by the functional core. As **Generators**, **Upgrades**, and prestige **Layers** transition to `'visible'`, the UI reveals their corresponding inline SVG badges, character guide commentary, and chronicle lore entries without introducing parallel reveal logic.
3. **Isolated Multi-Game Sessions and Shared Pacing Verification**: Each `GameConfig` carries a unique `id` (e.g., `dyson-swarm`, `aetherforge`, `sunken-observatory`), which namespaces its `StoragePort` persistence key (`inc_engine_save_${config.id}`) so players can switch games at runtime without losing progress. Every registered `GameConfig` is exercised by the `Simulator` test suite to guarantee monotonic progression, absence of deadlocks, and balanced prestige pacing across distinct mechanical parameters.
